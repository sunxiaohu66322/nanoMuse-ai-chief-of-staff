## 4. Worker 权限边界（本结论的核心风险）

### 4.1 官方原文（逐条带位置）

| # | 原文 | 位置 |
|:--|:--|:--|
| 1 | 「Executor Sessions run commands **without approval as the operator's OS user**」 | `docs/003-execution.md:27` |
| 2 | 「These wrappers and directories establish **defaults, not a security boundary**. **A worker can still execute a program by absolute path**.」 | `docs/003-execution.md:80` |
| 3 | 「Blocked commands fail **when invoked by name**」 | `docs/003-execution.md:78` |
| 4 | 「Directories are created under the configured execution root, which **defaults to `<stateDir>/work`**」 | `docs/003-execution.md:25` |
| 5 | 「the prepare command runs once **with `sh`** in the execution root. It has ten minutes」 | `docs/003-execution.md:51` |
| 6 | 「Only the panel can change execution environment settings; **text sent to the main Session cannot change the configured shell command**」 | `docs/003-execution.md:76` |
| 7 | 「Worker subagents … use … `standard` preset **with the worker's permissions**」 | `docs/003-execution.md:47` |

|:--|:--|:--|:--|:--|

### 4.3 风险判定

- **Worker 不是沙箱隔离** `[事实→推断]`：以主人 OS 用户身份、无审批执行 pwsh；`tool-fs` 可写；`shim + blockedCommands + stateDir/work` 只是**默认与约定**，官方明说可被绝对路径绕过。因此 **`executor.directory` 与 `prepare` 若不显式钉死，Worker 具备高权限访问无关项目的能力**——包括 9196 的代码/数据库、其它真实项目、以及 `I:\DSHHome` 下配置。
- **router 侧已收紧**：`tool-fs write:false/edit:false`、无 subagent、无 web `[事实]`。但 router 仍有 pwsh（`:139-162`），同样受 §4.1-1/2 约束。
- **PATH / git 隔离是「替换」不是「禁止」**：`<stateDir>/worker-gitconfig` 会替换全局与系统 git 配置并清 `GH_TOKEN`/`GITHUB_TOKEN`（`docs/006:225`），这降低误用主人凭据的概率，但**不构成对文件系统的边界**。
- **凭据渗出防护**：Setup 剥离名字含 KEY/PASSWORD/SECRET/TOKEN 的环境变量（`docs/006:218`）；但 `dsh-superagent-win.py:20,103,106` 会把 `RACCOON_GATEWAY_CRED` 注入子进程环境变量（**注入的是 SA 服务进程 env，非 Worker**；Worker 的 env 由 SA Setup 单独写，`[待验证]` 是否会继承该变量）。标为**待验证风险**，不冒充已排除。
- **`sh` 在 Windows**：prepare 命令官方以 `sh` 执行（`docs/003:51`），本机 `D:\tools\git-mini` 是否提供 `sh.exe` 未实测 `[待验证]`；`environment.root` 实测为 `\\DSH_Cache\state\superagent\work`（POSIX stateDir 在 win32 拼出的路径形态），prepare 若用 `git -C … worktree add` 需实测能否在该 root 落地。**P2 未跑，故此项未经真实验证**。

**缓解（写进 P1 设计，本轮不执行）**：把 `executor.directory` 与 `prepare` 严格限定到隔离测试仓库目录；`blockedCommands` 列入个人 `gh` 与危险绝对路径；专用账号 CLI wrapper；保持 `observe`；关闭 auto-merge；Worker 只接低风险只读/单文件任务。

## 6. observe 模式怎么保证「记录而不执行」——真实边界（重要纠正）

`docs/002-authorization.md:91-101` 原文：

```
| `off`     | Nothing inferred becomes a candidate …
| `observe` (default) | Inferred candidates are assessed; a positive assessment is
                        recorded as ignore marked "would accept", and nothing is accepted |
| `auto`    | A positive assessment of an inferred candidate accepts it |
Explicit requests work in every mode. Start in `observe` and switch to `auto` after reviewing the recorded Decisions.
```

实测 `blocks.eval.value.mode = "observe"` `[事实]`（`SETUP.md:58` 亦把 observe 列为默认）。

**必须讲清的边界** `[事实→推断]`：
- observe **只挡「inferred（主动推断）候选」**——未 @ 的消息、bot 消息、非白名单者的跟进；正评估记成 `ignore("would accept")`，不建 Ticket、不启动 Worker。
- **「Explicit requests work in every mode」**：白名单账号发 `@<agent> <request>` 属 explicit（`docs/002:13`「An allowed person who addresses the agent makes an explicit request」），**在 observe 下同样会被接受并真执行**。而 SETUP.md:77 / docs/006:231 的推荐试用法**正是**这种 explicit Issue。
- 所以「observe = 记录而不执行」**只对推断型工作成立，不是全局只读开关**。要真正「只记录不执行」，须叠加：`POST executor/pause {"paused":true}`（`docs/006:175`，`docs/003:192-200` 说明 pause 停止 dispatch/Eval/超时/投递/回复），或关闭 GitHub Source，或保持 setup 未完成（现状即如此，`runtime=paused/setupPending`）。
- 现状虽有 `paused=false`，但 runtime 因 `setupPending` 处于 paused（`docs/006:145`「Setup must succeed before polling or work starts」）——**当前事实上不会执行任何 Ticket**，这是安全态，别误当成故障去「修好」。

## 7. 自动合并怎么关（默认即为关）

`docs/003-execution.md:82-90` 原文要点：
- `:84` Auto-merge **由 `Delivery requirements` 提示词治理**，「The host has no merge-specific decision logic」（无平台侧开关，是提示词层）。
- `:86` 「By default, the Executor **never enables auto-merge as the agent account** … Without one, **people merge the pull request**」。
- `:90` 「**Omit the merge CLI or remove the auto-merge paragraph to require manual merging**」——这是关闭的确定做法。
- `SETUP.md:51` 问题 9 推荐答案 **No**，且明写「with no, **remove the auto-merge paragraph from Delivery requirements**」。
- `SETUP.md:86` 若选 Yes 还需另一个有合并权账号的 CLI 登录；本轮不涉。

**结论** `[事实]`：本机 `GET prompts` 的 `delivery` section 存在但**内容未逐字核验是否含 auto-merge 段落** `[待验证]`；官方默认 + SETUP 推荐答案均为「不自动合并」，且当前 setup 未完成、无 Ticket，**不存在自动合并风险**。P1 设计里把「显式确认 Delivery requirements 已移除 auto-merge 段落 + 不配 merge CLI」列为落地前置检查项，不执行。
