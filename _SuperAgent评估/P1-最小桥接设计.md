## 2. 桥接形态（三段闭环，全部走受支持接口）

```
┌──────────────────── 9196（唯一总控中心 · 不改代码） ────────────────────┐
│  ① 人工在总控台/对话里提出一个「已授权开发任务」                        │
│  ② 【硬前置】过 HIGH_RISK 审批闸门（见 §3）                             │
│  ③ 落 tasks(id, project_id, title, status='queued') + actions 行        │
│     生成受控 payload：NM_TASK_ID / NM_PROJECT_ID / 任务正文 / 验收标准   │
│  ④ 由 9196 的「下发适配器」把 payload 变成 GitHub Issue：               │
│     @<专用agent账号> <request>（Issue body 内嵌 NM_TASK_ID）             │
│     → 仅发往「隔离测试仓库」，用专用账号 CLI，绝不碰真实项目            │
└───────────────────────────┬───────────────────────────────────────────┘
                            │ HTTPS · 受控 Issue（官方唯一入口 docs/006:231）
┌───────────────────────────▼───────────────────────────────────────────┐
│  SA（3082 · 下属执行引擎 · 独立 profile / 独立 CLI / 独立 stateDir）    │
│  ⑤ GitHub Source 轮询 → Trigger → Policy gate → Eval → accept → Ticket  │
│  ⑥ Executor（worker preset）在隔离目录执行；产物 = commit / PR / Report  │
│  ⑦ 9196「回读适配器」轮询 GET tickets / GET tickets/:id / GET state     │
│     带 x-orchestrator-request:1；只使用 docs/006:169-179 公开路由       │
└───────────────────────────┬───────────────────────────────────────────┘
                            │ 状态/证据映射（§5）
┌───────────────────────────▼───────────────────────────────────────────┐
│  9196 复用现成端点回写：                                                │
│  POST /api/tasks/<id>/status  ·  POST /api/dsh-receipt                  │
│  POST /api/approvals/<id>     ·  POST /api/gantt/rebuild                │
│  → 映射回原项目 + 甘特，保留任务 ID / 执行记录 / 证据 / 去重            │
└─────────────────────────────────────────────────────────────────────────┘
```

**为什么不选别的形态**：
- **不直连 SA 数据库**：`docs/007:452` 单 SQLite、`:455-472` 表结构属内部实现，`:167` 明说其余路由「serve the panel and change with it」；直连会在升级时碎掉，且违反「优先复用官方接口/事件」。
- **不伪造调度 API**：`src/app/api.ts:20-45` 是完整契约，无 dispatch；任务明确要求「若无受支持调度 API，可评估受控 GitHub Issue 触发，但不得编造接口」→ 选 GitHub Issue，且每条都贴了 `docs/006:231` / `SETUP.md:77` 原文。
- **不改 9196 代码就能落地回写**：`/api/dsh-receipt` 已存在且语义正好是「外部执行引擎跑完回填」，`/api/tasks/<id>/status`、`/api/gantt/rebuild` 亦现成。**下发适配器**（把任务变 Issue）是唯一需要新增的薄件，建议作为独立小模块挂在 9196 外部、通过现成端点与 9196 通信，**本轮不写、不落地**。

## 3. 硬前置：9196 HIGH_RISK 审批闸门（lead 追加要求，最高优先）

**要求原文**：「9196 下发任务前先过现有 HIGH_RISK 审批闸门，不能因为 SA 有 Policy 就绕过 9196 的审批。」

**闸门真实实现（已核源码，非推断）**：

| 层 | 代码 | 行为 |
|:--|:--|:--|
| 词表 | `总管扩展.py:62-64` `HIGH_RISK = re.compile(r"删除\|删掉\|移除\|清空\|覆盖\|重写\|发布\|上线\|部署\|付费\|支付\|购买\|重置\|回滚\|drop\|delete\|push\|deploy\|publish\|overwrite\|reset\|rm\s-\|format", re.I)` | 命中即高风险 |
| 对话闸门 | `总管扩展.py:282-284` `detect_intent()` → `if HIGH_RISK.search(msg): return "approval"`；`:421-442` → **停止执行**、`_make_approval(…,"chat_high_risk")`、生成审批卡、回复主人 | 只登记，绝不执行 |
| 执行闸门 | `总管.py:683` `RISK_DENY`（删/覆盖/发布/上线/付费/direction/drop/delete/push/deploy）；`:686-706` `execute_action()` → 命中且 `not approve` → `status='approval_required'` + 写 `approvals(kind='high_risk')` + `emit("action.blocked")` + `notify`，返回 `approval_required` | 重大动作必须 approve=True 且单独批准 |
| 巡检闸门 | `总管.py:647-655` 待决策只登记 `direction_change` 审批；`总管扩展.py:483-488`、`:632-636` 定时推进命中高风险 → 生成 `auto_risk` 审批、**停止自动推进** | 自动链路同样不绕过 |
| 批准端点 | `总管.py:910-919` `POST /api/approvals/<id>` 写 `approved/denied` + `emit("approval.decided")` | 人工拍板唯一入口 |

**桥接必须遵守的四条（写死进设计，不是建议）**：

1. **先闸门、后下发**：任何发往 SA 的 `@<agent> <request>` Issue，**必须先让任务正文过 `HIGH_RISK` 判定**；命中 → 走 `POST /api/approvals/<id>` 生成待批卡，**绝不发 Issue、绝不建 Ticket**。审批 `status='approved'` 之前，下发适配器不得有任何 GitHub 写动作。
2. **SA Policy 不是替代**：SA 的 `policy.sources.github.allowed` + `eval.mode=observe`（P0 §6）+ `Delivery requirements` 只是**第二道**约束（`docs/002:91-106`、`docs/006:148`）。**observe 只挡 inferred 候选，explicit 请求在 observe 下照样真执行**（`docs/002:101`）——所以更不能拿「我设了 observe」当免审批理由。
3. **双向都要拦**：9196→SA 下发前拦一次；SA→9196 回读后若产物/Report 里出现高风险词（例如 Executor 报告 `push`/`deploy`/`published`），**回写 `tasks.status` 之前再过一次** `RISK_DENY`，命中则回 `approval_required` 而不是直接标 `done`。这防止「执行端绕过上游审批把状态洗成已完成」。
4. **权限不叠加、不提升**：SA Worker 以主人 OS 用户无审批执行（`docs/003:27`）、`tool-fs` 可写、shim「不是安全边界」（`docs/003:80`）——**9196 的审批闸门是唯一的授权边界**，桥接不得给它任何「已由 SA Policy 授权」的暗示字段。

**为什么这是硬前置而非可选项**：P0 已判 SA Worker 有高权限触及无关项目（含 9196 代码/库）的能力；若下发不经 9196 审批，等于把 9196 的「重大动作人工批准」机制架空。**lead 的追加要求与 9196 现有设计同向，直接复用即可，无需新机制**。

### 4.1 任务 ID 与去重（题设点名）

| Ticket Report `blocked` / `failed` | 失败 | `tasks.status='failed'`，`note=report`；可走 `POST tickets/:id/retry`（`docs/006:179`）后重新观察，**重试上限沿用 9196 的 2 次**（`总管.py:694-695`） | `/api/tasks/<id>/status` |

| Ticket `ended` 且 outcome=`merged`/`closed`/`completed`（`docs/005:32`、`docs/007:548`） | 成功 | `POST /api/dsh-receipt` 带 `{action_id, outcome:'succeeded', evidence, verified:true, session_id, project_id}` → 自动写 `actions.status='succeeded'` + `emit("dsh.receipt")` | `总管.py:920-930` |
| 产物就绪后 | 投影 | `POST /api/gantt/rebuild` 让甘特按 `tasks` 新状态重建（`总管扩展.py:532` 甘特读 `tasks`） | `总管扩展.py:714-716` |
| 任何回写前 | 闸门 | 再过一次 `RISK_DENY`（§3-3），命中 → `approval_required`，不标 done | `总管.py:683,698-706` |

**验收标准（DoD，写进任务正文随 Issue 下发）**：让 SA 交付「可核验产物」而非自报完成——`actions.checked=1` 的判据沿用 9196 既有口径（`总管.py:742-750`「产物已回读校验」）；SA 侧对应 `GET tickets/:id/result` + `/transcript` 有真实 commit/PR 链接，回读适配器**真的 GET 一次**才算 `verified:true`。**不许「接口 200 = 完成」**（主机铁律 18/21 同向）。
